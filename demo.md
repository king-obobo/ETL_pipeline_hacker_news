# Hacker News ETL Project Demo

## Demo goal

This is a walk through one end-to-end Python run, it includes: 
1. where a downloaded Hacker News story comes from, 
2. how the pipeline moves it through PostgreSQL, and 
3. how the run is verified.

## Running the pipeline

```powershell
uv run python -m scripts.pipeline --start-date 2026-10-01 --until 2026-10-04
```
This downloads the json file and saves it in the `data` folder.

The `--until` boundary is exclusive. The pipeline processes complete windows ending no later than `2026-10-04 00:00 UTC`; for six-hour windows, that is the 12 windows from October 1 through October 3. If the JSON files are already in `data/`, the downloader skips them unless forced to refresh.

## Walkthrough: what the Python run does

```text
scripts.pipeline
  -> connect to PostgreSQL; apply schema; read checkpoint
  -> download or reuse complete JSON window files
  -> scripts.etl discovers and validates files; plans the windows
  -> for each window, one transaction:
       batch log + raw staging + rejects + clean upsert
       + dimensions + fact upsert + checkpoint
  -> finish run and log extracted / loaded / rejected counts
  -> exit 0 on success, nonzero on failure
```

### 1. Orchestration and checkpoint

`scripts.pipeline` is the entry point. It retries the database connection while PostgreSQL starts, applies `sql/01_create_schema_tables.sql`, then reads `etl.checkpoint`. 

On a first run, the supplied `--start-date` defines the beginning. On incremental runs, planning begins from the checkpoint and includes the last two completed windows by default so changing story scores, comments, and other metadata can be refreshed.

Only complete UTC windows are planned. The API query uses `created_at_i >= start AND created_at_i < end`, so adjacent windows do not overlap. `--until` limits the run to windows ending at or before that date.

### 2. API request and downloaded file

`scripts.downloader` calls Algolia through `scripts.client`. The client retries transient connection errors, timeouts, rate limits, server errors, and invalid JSON. A range at the API's 1,000-hit cap is recursively split to avoid silently accepting a truncated response. The downloader validates the returned hit count and saves each window as JSON using a temporary file followed by an atomic rename.

For this example, the saved file is:

```text
data/hn_20261001T0000Z_20261001T0600Z.json
```

BASE_URL = "https://hn.algolia.com/api/v1"

ENDPOINT = f"{BASE_URL}/search_by_date"

PAGE_SIZE = 1000

The file contains a `meta` section (window bounds, source, counts, and fetch details) and a `hits` array. The story's source values are:

```json
  "updated_at": "2026-10-01T18:24:32Z",
```

### 3. File planning and run metadata

`scripts.etl` takes the local window files and determines which ones need processing. It verifies that each filename's time range matches the metadata inside the JSON, that `nbHits`, `hits_retrieved`, and the number of hits agree, and that the selected windows have no gaps or overlaps. It takes a PostgreSQL advisory lock so a second ETL load cannot run concurrently.

The loader creates an `etl.pipeline_runs` row for the run. Each processed JSON file gets an `etl.batch_log` row with its UTC window, status, and extracted/loaded/rejected counts. These IDs are generated by PostgreSQL; use the query below to find the IDs associated with the example story in the current run.

### 4. Raw staging: `stg.hn_stories_raw`

The story is stored first in `stg.hn_stories_raw`. Its source fields remain text at this layer:

| Staging column | Example value |
|---|---|
| `object_id` | `"49918200"` |
| `points` | `"4"` |
| `num_comments` | `"0"` |
| `created_at` | `"2026-10-01T05:57:05Z"` |
| `updated_at` | `"2026-10-01T18:24:32Z"` |
| `tags` | JSON text for the `_tags` array |
| `payload` | JSONB source hit, without `_highlightResult` |
| `run_id`, `batch_id` | Generated ETL metadata IDs |

Staging is append-only: a later re-pull adds another staged copy instead of overwriting the original record. The downstream clean layer resolves duplicates.

### 5. Validate and clean: `clean.hn_stories`

`scripts.transform` validates each hit before attempting typed conversion. It rejects a missing or non-numeric `objectID`, an invalid `created_at`, negative or non-integer points/comments, and a missing or non-array `_tags`. Rejected hits are written to `etl.rejected_records` with the reason and raw JSON payload. This example passes validation.

For this story, the clean transformation:

1. Converts `objectID` from text to `BIGINT` (`49918200`).
2. Converts points and comment count to integers (`4` and `0`).
3. Parses timestamps into timezone-aware PostgreSQL `TIMESTAMPTZ` values.
4. Trims fields and HTML-unescapes the title (there is no change for this title).
5. Finds neither `show_hn` nor `ask_hn` in `_tags`, so sets `story_type` to `regular`.
6. Computes `row_hash` from the cleaned title, URL, author, points, comments, and story type.

Within a run, duplicate IDs are reduced to one record, preferring the greatest `updated_at`. Against existing clean rows, the upsert changes content only if the hash differs and the incoming update is not older. An unchanged re-pull therefore does not count as a newly loaded fact.

### 6. Warehouse: dimensions and `dw.fact_story`

The pipeline derives the domain from the URL: `orthogone.com` (lowercase host, without `www.` or a port). It inserts the author and domain into their dimensions if they are not already present, then writes the fact row using the dimension keys:

| Fact field | Example value / derivation |
|---|---|
| `story_id` | `49918200` (from clean `object_id`) |
| `author_key` | Key for `mlhpdx` in `dw.dim_author` |
| `domain_key` | Key for `orthogone.com` in `dw.dim_domain` |
| `created_at` | `2026-10-01 05:57:05+00` |
| `hour_of_day` | `5` (UTC hour) |
| `story_type` | `regular` |
| `points` / `num_comments` | `4` / `0` |
| `has_discussion` | `false` (`num_comments > 0` is false) |

Dimension keys are generated by the database, so their numeric values depend on the actual load order. The fact table is reconciled against the values now in clean, preventing an older re-pulled record from overwriting a newer clean version.

### 7. Atomic window commit and checkpoint

For each window, staging rows, reject rows, clean changes, dimension/fact changes, batch counts, and checkpoint progress share one database transaction. If a window fails, that window's data changes roll back; the pipeline records the failed batch separately, stops rather than skipping ahead, and closes the run as failed. Earlier windows that committed successfully remain intact. A later invocation can resume from the checkpoint and retry.

After all planned windows succeed, the run is marked successful. The final console summary reports extracted, loaded, and rejected counts. `loaded` is the count of inserted or changed fact rows, not the total number of valid or staged hits.

## Analyze the data warehouse

These queries read from the `dw` schema, joining facts to dimensions where needed.

### 1. Which linked domains have the most stories?

```sql
SELECT
    d.domain,
    COUNT(*) AS stories,
    ROUND(AVG(f.points), 1) AS avg_points,
    COALESCE(SUM(f.num_comments), 0) AS total_comments
FROM dw.fact_story AS f
JOIN dw.dim_domain AS d USING (domain_key)
WHERE f.story_id < 99000000
GROUP BY d.domain
ORDER BY stories DESC, d.domain
LIMIT 10;
```

```sql

    a.author_name,
```

## The SQL-only alternative

The SQL path makes each database stage explicit: 
1. `01_create_schema_tables.sql` creates the schema, 

2. `02_load_staging.sql` imports the JSON files, 
3. `03_clean.sql` validates and upserts clean rows, and
4. `04_transform.sql` builds the warehouse and closes the run. After those steps, 
5. `05_validate.sql` checks the result. Unlike the Python entry point, the SQL loading script does not download from Algolia; it reads the files already mounted in `/data`.
